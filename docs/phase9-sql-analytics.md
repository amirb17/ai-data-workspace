3. **SQL execution engine selected and why.** DuckDB 1.5.6 runs in a disposable child process with registered authorized Arrow tables. The existing structured pandas analytics engine is retained for its existing callers; it does not provide a general SQL parser/runtime. PostgreSQL user-query execution would expose the control plane and is excluded. SQLite would require more conversion and offers poorer analytical/decimal support. DuckDB provides grouping, windows, exact decimals and typed Arrow integration without building a SQL interpreter. SQLGlot 30.22.0 provides a real DuckDB AST. CodeMirror supplies established editor behavior. Happy DOM is a development-only dependency for interactive component tests; pytz supports timezone conversion. The internal `SqlPlan` and engine adapter separate catalog/validation from execution so a future engine can be substituted without changing ownership or freshness policy.

4. **SQL dialect.** DuckDB is the advertised, parsed, formatted and executed dialect. CodeMirror uses its StandardSQL lexer plus workspace schema completion and the server's curated function list; this is highlighting guidance, not a second authoritative validator. Unsupported syntax fails closed. PostgreSQL compatibility is not claimed.

5. **Logical dataset namespace.** Display names are primary; SQL uses deterministic quoted aliases such as `orders_d1`, optionally qualified by `workspace`. The immutable identity suffix prevents an old alias from resolving to a different dataset when another dataset is renamed, removed or added. Renaming the referenced dataset changes its alias and makes old SQL require correction rather than silently rebinding it. Physical paths and database catalogs are unavailable.

6. **Trusted source policy.** Only the owned dataset's currently published successful cumulative Gold for its current state, with FRESH analytics and a current factual profile, is queryable. There is no Raw/Silver/delivery fallback. Immutable artifacts are read through the existing checksum/version boundary. Suggested business meanings guide authoring but are not silently approved. Ad hoc SQL does not turn unresolved metrics into approved definitions.

7. **SQL parser / AST validation.** SQLGlot parses exactly one SELECT with optional nonrecursive CTEs. Structural nodes, functions and scalar types are allowlisted. Table/column binding, star expansion, ownership namespace, complexity, depth and literal LIMIT/OFFSET are checked before artifact IO. Unknown future node classes fail closed. Parser fallback warnings are intercepted before they can log SQL literals. Formatting round-trips the parsed AST and preserves comments.

8. **Read-only security rules.** DML, DDL, COPY, ATTACH/DETACH, INSTALL/LOAD, PRAGMA/SET/CALL, SELECT INTO, recursive queries, multi-statements, unknown functions, external table functions, control-plane tables and system catalogs are rejected. Comments and quoted identifiers are parsed rather than matched with regex. Builder values become typed literal AST nodes and share the same validator.

9. **Engine sandbox protections.** A private in-memory DuckDB instance registers only projected authorized fields. External access, extension auto-install/load, unsigned extensions and disk spill are disabled; configuration is locked. One engine thread and a memory budget apply. The worker is destroyed after every execution. This is an application/engine sandbox, not an OS security sandbox: Arrow/pandas and Python allocations are additionally bounded by input checks but are not covered by a hard OS heap limit. No PostgreSQL connection or credentials are passed to the worker.

10. **Workspace isolation.** Catalog, query CRUD, execution and history all validate workspace ownership and scope by owner plus workspace. Database triggers reject mismatched metadata ownership and saved-query references. Frontend reads verify response workspace IDs; parent remounts, abort guards and user/workspace-scoped drafts prevent state leakage. Live navigation with a dropdown open to the empty fixture workspace cleared editor content, results and the portal. Production multi-user RBAC remains Phase 10.

11. **Query resource limits.** Defaults: 500 output rows, 1,000,000 response bytes, 250,000 rows per source, 500,000 aggregate input rows, 128,000,000 aggregate artifact/materialized bytes, 64 MiB per existing bounded artifact read, 256 MB DuckDB memory, one direct join/two datasets, 20,000 SQL characters, 1,500 AST nodes, depth 12, two concurrent executions per API process, 100 saved queries and 100 recent executions per owner/workspace. Environment configuration is clamped to policy ceilings. HTTP 429 reports occupied execution capacity. Output byte overflow returns no partial rows; row overflow is explicitly a truncated preview.

12. **Query timeout/cancellation.** A spawned worker has a 30-second execution deadline. The parent terminates, joins and, if needed, kills it; a real expensive-worker test verifies timeout and cleanup. Timeout returns no partial result. No fake Cancel control is offered. Navigation aborts client requests but does not claim to cancel server work. Metadata and S3 input loading happen before the worker deadline and are subject to separate size/read protections; the 30 seconds is not an end-to-end HTTP SLA. Deployment-wide admission control across multiple API processes is deferred.

13. **Schema browser.** Searchable owned dataset choices show Current or Refresh required, counts when current, logical aliases, physical field types, factual key/time information, semantic suggestions and unavailable sensitive fields. Stale options are disabled with reasons. Preview/count/category/time templates use current metadata and quoted identifiers, without inventing business definitions.

14. **Semantic/relationship guidance.** Roles and business meanings come from current Phase 7 evidence and are visibly labeled Suggested where appropriate. Only current confirmed relationships with current structural verification are shown. Guidance does not infer approval, grain or category mappings. Relationships display named child-to-parent endpoints, with technical references kept secondary.

15. **SQL editor capabilities.** CodeMirror provides line numbers, highlighting, indentation, bracket matching, scrolling, editable text and completion. Run, Validate, Format, Copy SQL, New, Save/Rename and Save as are available. Ctrl/Cmd+Enter runs, Ctrl/Cmd+S saves, Ctrl/Cmd+Shift+F formats. Syntax diagnostics include available line/column positions. Draft replacement asks before discarding unsaved text; scoped session recovery retains text only.

16. **Autocomplete.** Completion uses only current queryable logical tables and available columns, quoted names, SQL aliases, curated keywords and server-supported functions. Semantic details accompany field choices. Catalog changes rebuild completion; workspace changes destroy the previous editor. Tooltip portals avoid editor-container clipping. No AI request is made for completion or SQL execution.

17. **Builder behavior.** Typed dataset/output selections, COUNT/COUNT DISTINCT/SUM/AVG/MIN/MAX, up to three grouping fields, four filters, compatible operators and numeric/date/boolean inputs, selected-output sorting, bounded row limits and optional confirmed lookup generate SQL via SQLGlot. SUM/AVG accept numeric measures; MIN/MAX accept numeric/date fields. Dataset changes clear dependent selections. View/Edit SQL is intentionally one way: arbitrary SQL is not falsely represented as a reversible Builder form. Safe categorical enumerations are unavailable from the redacted profile context, so literal value entry is used; no sensitive or high-cardinality enumeration is fetched.

18. **Join policy.** V1 permits one direct single-key INNER/LEFT current confirmed child-to-parent lookup, with ONE_TO_ONE or ONE_TO_MANY evidence. Parent-to-child fanout, unconfirmed/stale joins, cross joins, multi-hop/derived joins, USING/NATURAL and non-equality keys are blocked. Multiple datasets in subqueries cannot bypass the relationship requirement. Current runtime parent uniqueness, nonnull keys and FK coverage are rechecked before execution. The policy conservatively blocks nullable child keys. Builder outputs base-dataset fields; SQL can select parent fields.

19. **Result table behavior.** Genuine engine rows appear in an internally scrollable table with sticky typed headers, 50-row paging, exact local sorting, cell copy and long-value expansion. Sorting/paging apply only to returned rows. Zero rows, blocked queries, failures, timeouts and truncated previews have distinct truthful messages. Historical records show metadata and require rerun for rows.

20. **Precision/null/time handling.** SQL NULL remains JSON null and displays NULL, distinct from empty string, false and zero. Decimal results and integers above JavaScript's safe range are serialized as exact strings. Decimal/large-integer sorting uses exact BigInt arithmetic. Date/timestamp values use ISO strings; timezone-aware execution uses UTC. Nonfinite floating values become null; unsupported complex result types are blocked. UI formatting does not recalculate aggregates.

21. **Result chart behavior.** Bar and line charts use only returned compatible rows with explicit X/Y selections and no invented grouping or aggregation. At most 100 unique, nonnull X values are charted. Exact decimal/large-integer strings remain in the table when charting would lose precision. Line charts require actual DATE/TIMESTAMP values and at least two points, ordered by time. Incompatible selections explain the table fallback. Charting a bounded preview is not presented as a full dataset statistic.

22. **Saved queries.** Owner/workspace-scoped names, descriptions and SQL text have optimistic versions and a bounded quota. Create, rename/update, Save as, duplicate draft, reopen and explicitly confirmed delete are supported. Saved SQL is never silently repaired or automatically run. Live save/reload/reopen/rerun returned the literal status count 2. Deleting a saved query preserves historical execution references; the real DB test verifies it.

23. **Query history.** Terminal metadata records are immutable under UPDATE protection and scoped to the owner/workspace. Retention deletes only older SQL execution metadata beyond the configured bound. History contains authored/normalized SQL, timestamps, status/diagnostics, row counts/truncation, runtime/configuration and source/relationship pins. Result rows are never stored in PostgreSQL or browser storage. Query text can contain user-entered literals and is therefore private owner-scoped metadata, not telemetry.

24. **Freshness/provenance.** State, Gold, profile and relationship versions are pinned. Signatures are checked after calculation and again under workspace/dataset locks before publication; changed inputs discard rows and record SOURCE_CHANGED. Read-time history and periodic frontend metadata refresh label old successful results Data changed. Live stale-source verification preserved the historical label and blocked a new execution. The DB test verifies APPEND, stale blocking, refreshed rerun and changed provenance.

25. **Result reproducibility.** History preserves exact SQL, normalization, engine version, configuration and immutable source pins. The query hash includes these dependencies. Rerun intentionally uses current validated sources and produces a new execution; historical rows are not cached or replayed as current. A prior configuration/source identity can be inspected, but V1 does not offer arbitrary historical artifact execution or export. Identical unordered queries are not promised stable row ordering without ORDER BY.

26. **Sensitive-data handling.** Fields marked by current sensitivity hints and operational metadata fields are excluded from execution projection and star expansion. Direct reference is rejected before IO. No raw sensitive/category sample lists, credentials, storage paths or unrestricted source access are sent to AI or exposed through catalog/results. This classification is as strong as the existing current evidence; it is not a claim of complete PII detection or new masking/RBAC functionality.

27. **Logging/observability.** Application logging records execution/workspace/principal IDs, status, duration, source IDs, row count and truncation. It does not log SQL text/literals, result rows, paths or credentials. Public exception messages are redacted. Parser command fallback no longer emits SQL text, verified by a log-capture test. Saved query conflicts, invalid requests and capacity errors receive SQL-specific safe frontend messages.
