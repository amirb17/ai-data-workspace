# Phase 5A — backend business-rule approval bridge

## Scope and behavior

Completed upload → explicit Prepare Rules (Bronze) → backend profiles/schema
fingerprint → AWAITING_RULES → explicit answers → Save Answers → explicit
Finalize / Approve Rules → READY_FOR_SILVER. Finalization never runs Silver/Gold.

Dataset remains the processing boundary. Frontend contracts remain local schema
and load expectations; no contract field is copied into business-rule answers.
The delivery uses its PostgreSQL upload request identity, not its local batch ID.

## Existing architecture reused

Questions come from Bronze profiles and semantic column classification in
`rule_suggestion_service`. Generated types are UNIQUE, NOT_NULL, DATA_TYPE,
ALLOW_NEGATIVE, and DUPLICATE_HANDLING. Controls render the backend's options
only, with an unanswered placeholder. VALID_DATETIME exists in the rule engine
but is not currently generated by this suggestion service.

Answers/rules are dataset-version scoped. Changed submissions increment the
existing integer `rule_version` once; identical submissions do not. Existing
active rule selection is preserved. Silver reads the current dataset-version
rule counter and active business rules. Saved draft answers can create active
rows, but approval remains gated by the association lifecycle. The UI calls
these DRAFT until finalization produces READY_FOR_SILVER; it does not invent an
independent ACTIVE version record or finalization timestamp.

The existing system retains historical run/version identifiers and results,
but does not retain immutable snapshots of each older rule definition. Full
historical rule replay/version management is outside this bridge.

## APIs

Reused under `/files`:

- POST `/uploads/{upload_id}/process`: Bronze only. Now validates the development
  principal, completed upload, workspace/dataset ownership/context, and source
  file. Returns the public processing context rather than private storage paths.
- GET `/dataset-version-files/{id}/business-rules/suggestions`: backend questions,
  saved answers, current version/state, active rule count; also supports reads
  after finalization.
- POST `/dataset-version-files/{id}/business-rules`: explicit draft answer save.
- PATCH `/dataset-version-files/{id}/business-rules`: existing answer update,
  now ownership checked and validated against the question's options.
- POST `/dataset-version-files/{id}/business-rules/finalize`: explicit approval.

Added GET `/uploads/{upload_id}/processing-context`: public upload/file/dataset
version/association identifiers, actual status, rule version/state, active rule
count, and Silver prerequisite boolean. No private object locations or exception
details are returned by the bridge.

Frontend requests include workspace/dataset context and writes include
`expected_rule_version`. Legacy writes may omit the version guard for backwards
compatibility, but the bridge always sends it. Ownership is enforced even when
scope query parameters are omitted. Stale writes return 409. Mutation operations
lock the dataset version, reject active downstream attempts, and use one shared
repository transaction for answer/config writes and the counter/status update.

Save validates every answer before writing anything, including duplicate answers
and cross-type options. Finalization refuses unanswered/unresolved questions and
also refuses zero active rules, matching Silver's existing prerequisite.

Repeated Bronze uses an atomic conditional association update: only UPLOADED
becomes AWAITING_RULES. Ready, running, failed-downstream, and successful states
remain unchanged, including under repeated requests.

## Schema repair

Migration `0008_dataset_version_file_status.sql` records the lifecycle status
column already present in the live development schema. It also relaxes legacy
`business_rules.file_id` and `business_rule_answers.file_id` nullability so the
existing dataset-version-scoped writes work on fresh installations. Isolated
tests revealed that the recorded earlier migrations omitted those adjustments.
The live test successfully saved rules without needing a live schema change.
No new tables or rule-version architecture were introduced.

## Limits and next step

- Rules selection uses existing local delivery discovery; clearing local batches
  does not delete backend rules, but removes those deliveries from this selector.
- No explicit approval timestamps or immutable historical rule snapshots exist
  in the current schema; the UI does not manufacture them.
- No generated questions / all rule-disabling answers remain blocked without
  active rules. Defining additional rules belongs to later rule management.
- Rules are shared within a dataset/schema version; sources of the same physical
  content share an association. Approval does not create per-upload rule copies.
- Physical-file Bronze cache/recovery and the legacy Silver/Gold routes retain
  their existing broader limitations; safe execution integration is Phase 5B.

Phase 5A is ready for review. The next authorized phase would integrate Silver/
Gold, authoritative attempt outcomes and recovery using this approval/status
foundation. This task does not implement that phase or commit changes.
